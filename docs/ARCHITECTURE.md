# Architecture

Generated by `/arch`; describes only what exists in code.

## Overview
Expenses come in from a batch file or the React portal. Each passes an input guard, deterministic
normalisation, LLM fact extraction and a pure policy engine; flags get an LLM-drafted question.
Every decision is an append-only revision, delivered downstream through an outbox and pushed to
the UI over SSE. Portal work runs in background jobs.

## Components
| Module | Responsibility |
|---|---|
| app/guard.py | schema/length, sanitise, manipulation screen (Decisions API -> Claude -> regex); reject vs suspect bands |
| app/normalize.py | USD amount and date parsing; flags non-dollar currency symbols |
| app/llm.py | Decisions API screen, Claude screen, extraction, question drafting |
| app/policy.py | pure rules -> decision + reasons (caps, receipts, codes, split, duplicate, high amount, future/stale date, placeholders, multi-night hotel) |
| app/pipeline.py | evaluate (pure) + process/process_stored (locks, store, notify) + human override + failure flag |
| app/jobs.py | background decision workers; per-id coalescing; startup recovery |
| app/outbox.py | atomic claim, retry with backoff, idempotency key, supersede; Finance retry (one attempt, latest revision only) |
| app/store.py | SQLite (WAL): expenses, expense_versions (append-only), decisions, followups, idempotency keys; atomic batch insert; filtered/paged list (`query_expenses`, whitelisted sorts); stats |
| app/server.py | FastAPI REST + SSE; serves frontend/dist with SPA fallback |
| frontend/ | React SPA: /employee/*, /finance/* |
| batch.py / eval.py | batch run / labelled-data scoring |

## Decision flow
```mermaid
sequenceDiagram
  participant UI as Portal
  participant API as server.py
  participant J as jobs.py
  participant P as pipeline.py
  participant O as outbox.py
  UI->>API: POST /api/expenses
  API->>API: expense_lock: upsert, status=checking
  API-->>UI: 202 checking
  API->>J: enqueue(id)
  J->>P: process_stored(id)
  P->>P: guard -> normalize -> extract -> policy (employee_lock)
  P->>P: question if flag; add_decision (revision, decision_key)
  P-->>UI: SSE decision
  P->>O: deliver(id, revision)
  O->>O: claim -> POST /decisions (retry with backoff)
  UI->>API: POST /answer (reply + fields)
  API->>J: enqueue(id) -> re-evaluate with the reply
```

## State & data
`expenses` (current raw, normalised, replies, version, status), `decisions` (append-only revisions:
exact payload, signals, delivery state), `followups` (question, answer, open/answered/superseded).

## Safety boundaries
- Code decides: app/policy.py (tests/test_policy.py)
- Guard first, reject only when confident and located: app/guard.py run_guard (tests/test_guard.py)
- Fail closed: pipeline.evaluate step 5, jobs failure flag (tests/test_adversarial.py, tests/test_races.py)
- A reply can't flip a decision: re-evaluation only (tests/test_server.py, test_races.py)
- Human decision is final per version: pipeline._decide_locked (tests/test_races.py)
- Stored == POSTed: payload_json is the body sent (tests/test_server.py)

## LLM providers & fallback
Guard: OpenAI Decisions API (`gpt-6-luna`) -> Claude screen -> regex backstop. Extraction and
questions: Claude (`LLM_MODEL`, default claude-haiku-5-5), with a template fallback for questions.

## Failure modes
LLM down -> flag. Endpoint down -> outbox retries, then `dead` (shown on the dashboard).
Process crash -> `checking`/`error` re-queued and stale `sending` reset on startup.
